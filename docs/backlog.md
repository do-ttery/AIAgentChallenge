# 빨래집사 백로그

> 4주 안에 **무엇을 · 언제 · 누가** 할지 정해두는 문서. 개발 중에 흔들릴 때 여기로 돌아옵니다.

## 백로그란

백로그(backlog)는 **아직 하지 않은 일을 우선순위 순으로 쌓아둔 목록**입니다. 원래 스크럼에서 나온 개념으로, 핵심은 "할 일 목록"이 아니라 **"순서가 있는 할 일 목록"**이라는 점입니다.

**왜 필요한가.** 4주는 하고 싶은 걸 다 하기엔 짧습니다. 백로그가 없으면 그때그때 눈에 띄는 걸 하게 되고, 마지막 주에 "정작 데모에 필요한 게 안 됐네"가 됩니다. 백로그의 진짜 역할은 할 일을 적는 게 아니라 **뭘 안 할지, 뭘 나중으로 미룰지를 미리 정해두는 것**입니다. 그래서 P0/P1/P2 우선순위가 목록 자체보다 중요합니다.

**어떻게 생겼나.** 한 줄이 하나의 Task이고, 각 줄에 최소한 이만큼이 붙습니다.

| 항목 | 뜻 |
|---|---|
| ID | 대화·커밋·PR에서 참조할 이름 (`T-08`) |
| Task | 큰 단위의 결과물. "무엇이 되면 끝인가"가 보이게 |
| 우선순위 | P0 / P1 / P2 |
| 담당 | 한 명. 둘이면 아무도 안 함 |
| 주차 | 언제 할지 |
| 의존 | 이게 끝나야 시작 가능한 선행 Task |
| 상태 | 대기 / 진행 / 완료 |

**어떻게 관리하나.** 세 가지만 지키면 됩니다.

1. **작업 시작 전에 상태를 `진행`으로 바꾼다.** 둘이 같은 걸 잡는 사고를 막습니다.
2. **주차가 끝나면 다시 정렬한다.** 백로그는 한 번 쓰고 마는 문서가 아니라, 매주 우선순위를 다시 매기는 살아있는 문서입니다. 안 끝난 P0는 다음 주 맨 위로, 못 한 P2는 미련 없이 버립니다.
3. **새 아이디어는 여기 맨 아래에만 적는다.** 코드에 바로 손대지 않습니다. 범위 확장(scope creep)은 이렇게 막습니다.

## 우선순위 기준

우선순위는 "중요해 보이는가"가 아니라 **"없으면 데모가 성립하는가"**로 정합니다.

| 등급 | 기준 | 못 하면 |
|---|---|---|
| **P0** | 없으면 핵심 흐름이 끊긴다 | 데모 자체가 불가능 |
| **P1** | 있어야 흐름이 완결된다 (분기 · 예외) | 데모는 되지만 반쪽 |
| **P2** | 있으면 좋다 | 버려도 무방 |

## 역할

| 담당 | 영역 |
|---|---|
| **서원** (`swlog`) | `client/` 화면 3개 · 디자인 시스템 적용 · 시뮬레이터 (백엔드 보조) |
| **도경** (`do-ttery`) | `server/` Express · SQLite · 상태 머신 · 알림 · Tapo 센서 연동 |

레이어(프론트/백엔드)로 나눴습니다. 화면별(고객/점주)로 나누지 않은 이유는 **두 화면이 같은 상태 머신과 같은 `session` 테이블을 보기 때문**입니다. 상태 머신은 어느 화면에도 속하지 않는 공통 심장이라 화면 기준으로는 잘리지 않습니다.

경계에서 만나는 지점은 **[CLAUDE.md](../CLAUDE.md)의 API Spec과 Data Model 하나뿐**입니다. 이미 확정돼 있으므로 서로를 기다릴 필요가 없습니다. 프론트는 그 구조 그대로 mock을 만들어 화면을 완성하고, 나중에 mock만 `fetch`로 갈아끼웁니다.

백엔드 쪽 짐이 훨씬 무거워서 **시뮬레이터(T-21)는 서원이 맡습니다.** 프론트가 화면을 실제 데이터로 돌려보려면 어차피 필요하고, 백엔드에서 가장 무거운 짐 하나를 덜어줍니다.

**게이트 3개 전부 통과.**

- ✅ 정격 전류 10A < 16A (P110M 한계) — 1.1kW면 220V 기준 실사용 약 5A. 여유 넉넉
- ✅ 콘센트 방식 (직결 배선 아님)
- ✅ 매장 Wi-Fi 사용 가능

### ⚠️ 정격 입력 1.1kW가 의미하는 것 — T-05의 핵심

20kg 업소용인데 1.1kW라는 건 **전기 히터가 없다**는 뜻이다 (온수를 배관으로 받는 방식). 가정용 세탁기(히터 2~3kW)와 전력 곡선이 근본적으로 다르다.

**좋은 점** — 히터라는 큰 배경 부하가 없으니 모터 고속 회전이 유일한 대형 부하다. **탈수 스파이크가 매우 뚜렷하게 튄다.** RUNNING → SPIN 전이는 쉽게 잡힐 것이다.

**위험한 점** — 히터가 없으면 세탁 중 전력이 **모터 텀블(돌다-멈추다-돌다)만 따라간다.** 즉 **세탁 중에도 전력이 주기적으로 0W 근처까지 떨어진다.**

State Machine의 종료 판정은 이렇게 정의돼 있다.

> SPIN → DONE : 전력 0W 복귀 **유지**

**세탁 중 텀블 휴지기에 0W가 찍히면 종료로 오판한다.** "유지"가 몇 초인지가 전부다. 이 숫자를 놓치면 3주차 상태 머신이 세탁 중간에 "완료!" 알림을 보낸다.

**→ 실측 당일 반드시 잴 것: 세탁 중 텀블 휴지기가 최대 몇 초인가.**
종료 판정의 "유지" 시간은 그보다 넉넉히 길어야 한다. 이걸 안 재면 매장에 다시 가야 한다.

### 매장 가기 전에 끝내둘 것

세탁 1회가 40~60분이라 현장 시간이 길다. 아래를 미리 해두면 도착해서 바로 돌릴 수 있다.

- Tapo 앱 설치 · 계정 생성 (매장에선 **등록만**)
- 세탁 표준 코스 소요 시간 확인
- `pip install python-kasa` + 폴링 스크립트 뼈대 작성 — **IP 한 줄만 비워두고** 나머지(5초 루프·재시도·CSV·`/ingest` 전송)를 다 짜둔다. 매장에서 `kasa discover`로 IP만 넣으면 바로 돈다
- 실측 손기록 양식 준비 (아래)

**폴링 간격 주의** — CLAUDE.md 기준은 5초다. 텀블 휴지기가 5초보다 짧으면 폴링이 통째로 놓친다. 실측만큼은 **1초 간격으로 찍어서** 휴지기의 실제 길이를 먼저 확인하고, 그 결과로 운영 폴링 간격이 5초로 충분한지 판단한다.

## 2주차 완료 정의 (Definition of Done)

다음 주까지 아래 네 가지가 되면 2주차는 끝난 것으로 봅니다.

1. ✅ **`npm run dev` 한 번으로 `client`(5173)와 `server`(3000)가 같이 뜬다.** (T-01 완료)
2. **화면 3개(QR 랜딩 · 진행 · 대시보드)가 mock 데이터로 완성돼 있다.** 디자인 시스템(색·라운드·마스코트·문구 톤) 검증 체크리스트를 통과한다.
3. **실제 세탁기 1회의 전력 곡선이 CSV로 찍혀 있고, 상태별 W 임계값이 문서에 숫자로 적혀 있다.** (T-05 — 여기서 막히면 즉시 공유)
4. **시뮬레이터를 돌리면 `POST /ingest/:machineId`가 데이터를 받는다.** (아직 상태 판정은 안 해도 됨)

2주차가 끝나면 이 문서를 다시 열어 우선순위를 재정렬합니다.
